# The travel graph is authored, never derived at build time

Authoritative for `data/travel.json`, walk edges, route costs, `access`, `overrides`,
adjacency and doorway resolution, and `scripts/derive_travel_graph.py`.

Part of the `eql-interactive-map` reference set, pointed at from `AGENTS.md`'s routing table.
**`AGENTS.md` states the rules; this file carries the reasoning behind them** — the measured
figures, the alternatives tried and rejected, the derivations. Where the two disagree, that is a
bug to fix in place, not a precedence question.


`data/travel.json` is hand-edited. `scripts/derive_travel_graph.py` bootstraps and audits it; it is **not** part of the build. `build.py` preserves its `walk` array as the unchanged prefix of injected `TRAVEL`, then appends edges already costed in the generated discovery catalog. It never derives geometry or cost itself, and an absent authored graph stays `{}` rather than becoming a schema-incomplete discovery graph.

Adjacency *is* derivable from committed geometry — measured on current data, connector endpoints resolve to two distinct zones **62/62** via the viewer's own `nearestZoneForPoint` at `ANCHOR_THRESH=1200`, hubs resolve to a host zone **41/41**, and welds ∪ connectors ∪ `manual` links makes every multi-zone continent one connected component. That makes derivation a good bootstrap and a bad runtime dependency: routing topology is a fact about the game, zone placement is a drawing decision, so deriving on every build lets a cosmetic zone nudge silently add or drop a travel edge — and `datacmp` cannot flag it, because the injected data legitimately changed.

**The same argument governs every cost authored in `data/travel.json`.** `zoneCentroid()` is `[z.cx+xf.tx, z.cy+xf.ty]` — rotation and scale are about the centroid so they cannot move it, but `tx/ty` can. A cost computed from transformed centroids at runtime would therefore shift when an author drags a zone for looks, and reading it through `contData()` would let a *user's* customisation change their own routing. So the bootstrap writes a default cost from **untransformed** stored `cx`/`cy` and the runtime never reads centroids at all. Cost of this choice: staleness. `--audit` re-derives and *reports* differences and must stay a report; `--recost` is the separate, explicitly invoked action that writes them. Neither may become a build step that silently reconciles — the point is that a cosmetic zone nudge cannot change an authored route without someone deciding it should.

**An unrostered discovered zone is the bounded exception, not a weakening of the authored rule.** Detection accepts only keys absent from every `zoneOrder`, while `verify.py travel` rejects an authored edge whose endpoint is outside those rosters, so the authored and discovered edge sets are structurally disjoint. Conversion derives the discovered placement, doorway and cost once and records all three in the generated manifest; build appends the stored edge without recomputing it. A user overlay remains runtime-only and cannot reprice anything. The real hazard is an explicit reconversion against a different pack: its traced placement can move, and its derived cost can move with it. The build assertion against an authored-pair collision documents that fence for future discovery-rule changes; it is not present-day coverage, because the two sets cannot currently intersect.

**The reusable cost model lives in `scripts/mapgeom.py`, and arithmetic that can reach injected data must use its explicit `sqrt(dx*dx + dy*dy)` norm, never `hypot`.** CPython `math.hypot` and JavaScript `Math.hypot` disagreed on **21,015 / 60,000 (35%)** continent-scale inputs measured 2026-08-08; the explicit Python/JavaScript `sqrt` forms disagreed on **0 / 60,000**. The adjacent cross-language rules are part of the same boundary: one decimal place is half-even rounding of `x*10`, then division by 10 — not Python `round(x, 1)` or JavaScript `toFixed(1)`. **No trig on the cost path.** Nothing that produces a `cost` may use `cos`/`sin`; they diverged on about **2.4%** of random angles. `tpoint`/`tinv` are the deliberate exception — they are frame transforms, not cost arithmetic, and every value they produce is rounded to one decimal before it can reach the injected data, which absorbs the divergence by many orders of magnitude. **A JavaScript twin of `tpoint`/`tinv` does not inherit that safety for free: it must be checked for parity against Python, not assumed.** `mapgeom.py` states the executable contract beside the implementation; this reference owns why those operations are forbidden.

**`src/mapgeom.js` is the dependency-free classic-script/CommonJS twin of that module.** Its
non-trig `norm` and untransformed `costBetween` boundary is raw IEEE-754 bit equality with Python;
its `tpoint`/`tinv` boundary is half-even `round1` output with negative zero canonicalized. The
module is verifier-only at present: no production converter or builder consumes it, so adding or
changing it cannot alter a built map until that seam is deliberately connected.

The zone resolver consequently has three named copies: `scripts/mapgeom.py`, `src/template.html`,
and `src/mapgeom.js`. `travel-full.test.js` guards the template/Python edge through authored-cost
parity; `mapgeom.test.js` guards the Python/JavaScript edge across the full tables and first-wins
index behavior.

**`links[].deleted` is an editor rigid-group signal, not a statement that two zones don't connect.** Do not subtract deletes blindly when deriving adjacency — on current data that shatters Antonica into 4 components and strands `arena`, `cazicthule`, `guktop`. The working rule is *deleted **and** a connector is drawn ⇒ still adjacent; deleted **and** no connector ⇒ proximity false positive*. It is right on most of the 14 deleted entries, not all: `guktop`↔`innothule` is real and the rule rejects it, because that connector's endpoint resolves to Lower Guk instead. Which is why the bootstrap reports every ruling instead of trusting itself.

**`META.gscale` is not a physical scale and must not be used to normalise distance.** It is a cosmetic globe-fit factor: Plane of Fear's 2 813 continent units and Antonica's 57 118 both land at 14–25 globe units. Raw stored units are the distance proxy, with the caveat that per-continent frames were assembled independently, so cross-continent comparability is assumed rather than established.

**Walk cost is centroid → the doorway each zone names → centroid, *not* centroid separation and no longer the outlines' closest approach.** The continental stitch does not place zones at true relative distance: Innothule Swamp and South Desert of Ro are drawn 13 800 units apart with nothing between them, and 15 of 76 authored pairs have outlines that never come near touching. A connector between two zones means they are directly connected whatever the drawing puts between them, so that void must not be priced — under plain centroid separation it made `innothule ↔ sro` cost 64.8, the most expensive edge on the map, four fifths of it empty canvas. Closest approach fixed that and introduced its own error, because it is only a valid proxy where the outlines actually touch; the doorway now comes from the zone's own `to_X`/`from_X` detail label, the same primary source the drawing uses, so **the drawn line and the price measure one path**. Costs move both ways: `innothule ↔ sro` rose 14.9 → 23.1 once the crossing was put at Innothule's real northern entrance rather than its east flank, while `northkarana ↔ southkarana` fell 37.2 → 29.1. Recosting all 74 edges moved the **sum by +0.1%**, which is why the calibration below survived it.

**A route dog-legs through the middle of every zone it passes through, and that is the node model, not a bug.** A graph node is a *zone*, represented by one point — its stored centroid — so every leg is centroid → doorway → centroid and a pass-through zone is necessarily crossed doorway → centroid → doorway. A player would cut straight between the two doorways. It is most visible on wide zones entered and left at opposite edges: North Karana is 6 400 × 6 100 units with its East Karana doorway at 97% across and its West Karana one at 2%, and the centroid sits below the line between them, so the drawn route dips to it and back — 30.2 units against 25.2 straight, **20% over, ≈37 s**. Systemic, and North Karana is mid-pack: worst per intermediate zone is Rivervale at **28.2** units overstated (misty → kithicor), then Nektulos 15.6, Runnyeye 14.7, East Commonlands 13.7, Feerrott 13.2. Two things stop this being a quick fix. Cost and drawing currently *agree* — both go via the centroid — so cutting the corner in the drawing alone would break that and move the pip off its own line. And pricing a pass-through properly cannot be a per-edge number: it depends on which doorway you arrived by, so nodes would have to become `(zone, doorway)`, tripling the node count and changing every cost. Note also that doorway-to-doorway straight line is itself an idealisation with no terrain in it, so the truth lies between the two figures and the centroid version is the conservative end.

**One cost unit is worth about 7.4 seconds, and every authored route cost hangs off that.** The anchor is the overland Freeport→Qeynos run through the Karanas: the graph prices it at 243.6 units and it is remembered as roughly half an hour. Everything else was set against it — a self-cast port at **30** (≈3¾ min: memorise, cast, med, and you land at a ring rather than at your destination) and a boat at **45 per hop** (≈5½ min, so the two-hop Ocean of Tears crossing is ≈11 min including the wait). Nothing in `data/` records this, so re-derive nothing without it. Note that `mapgeom.py`'s `UNITS_PER_COST = 250.0` sets only the *walk* scale; neither `--audit` nor `--recost` ever touches a route's **vehicle** `cost`, so bootstrapping a new continent yields walk edges on this scale and vehicles on whatever you write.

**Re-deriving costs is `--recost`, and it is deliberately not `--audit`.** `--audit` is the passive drift report and must never write. `--recost` is the explicit author action, and it rewrites exactly the two things geometry determines: `walk[].cost` and `routes[].access`. Everything else passes through untouched — topology, `at`, `overrides`, `groups`, `capabilities`, and each route's hand-set vehicle `cost`. It works over the **authored** edge set rather than the proposal, which is what lets it also price the `overrides.added` edges that geometry does not derive by construction yet whose doorways their zones name perfectly well.

**The derivation tool refuses a partial cache before every mode, including `--audit`.** Its
geometry loader walks the complete authored `zoneOrder`, so an undeclared file miss would otherwise
surface as a bare file error; more importantly, `--recost` could rewrite authored costs using an
incomplete map. The guard reads manifest `skippedZones`, names each affected continent and count,
and requires a complete re-import. This is stricter than the runtime, which is intentionally able
to route over whatever zones a partial build contains.

**The Python resolver is a second copy of `znorm`/`ZIDX`/`ZALIAS`/`LINK_OVERRIDE`, and one test is what stops it drifting.** `travel-full.test.js` recomputes every authored cost from the *template's* resolution and requires exact agreement, so a table that falls out of step surfaces as a cost mismatch instead of a quietly wrong route. Two traps found while wiring it: `ZIDX` is first-wins over genuinely colliding keys, but the two copies do **not** share an insertion-order contract — Python walks `world.json` order and `zoneOrder` within, while the viewer walks `DETAIL`, assembled in `detailZones` order. They resolve identically on current data only because the three colliding groups (`neriak`, `kaladim`, `felwithe`) retain their internal order in both lists. Aligning the orders could therefore move authored costs on future data, though it would not on today's data, so that behaviour change is outside a no-output-change extraction; and the check must work **untransformed** — `nearestOutlinePointTo` applies `tPoint` because the *drawing* must follow a viewer's moved zone, so calling it from a cost comparison mixes frames and disagrees by tenths.

**Port cost is what stops the walk graph becoming decorative, and the tell is a short trip, not an aggregate.** At the bootstrap's port cost of 3 — below the median single walk edge of 13.1 — 36% of directed adjacent zone pairs routed *through a port to reach the zone next door*, and the planner told a player at the Cazic-Thule exit to cast a port into The Feerrott. "95% of trips use a port" is **not** itself the bug: for a druid, porting usually is right. At 30/45 plus `access` that falls to **2 of 148** directed pairs, **all 74** walk edges appear in some optimal route, and the boats survive as the ungated inter-continental path. `travel-full.test.js` declares those two by name so a third fails. The list has shrunk twice and both times that was the model sharpening: recosting from the doorways dropped North/South Karana (29.1, under a port's 30), then pricing the in-zone walk to a hub dropped four more. The survivor is **asymmetric for a modelled reason** — West Karana's spire is 32.4 of access, so arriving there costs 62.4 against a 47.3 walk and porting loses, while arriving at North Karana's costs 35.1 and it wins.

**A dungeon-entrance cost floor was measured as unnecessary — do not add one.** The concern is real in principle (centroid separation is a poor proxy for a dungeon entrance, and Kedge Keep ↔ Estate of Unrest prices at 1.1), but a mispriced edge can only produce a wrong answer if a route passes *through* it, and every dungeon in this graph is a dead end. Of the 44 zones that ever appear as an intermediate hop, the only dungeon-ish ones are Blackburrow and Upper Guk, and both are genuinely pass-throughs.

**Weld gap discriminates real zone lines from proximity artifacts; weld-only-ness does not.** Two thirds of the graph arrives from welds alone, so flagging every weld-only edge for review produced 54 items of noise. Filtering to welds whose outlines never actually meet (`NEARMISS_GAP=20`) cut that to 11 and still caught the known false edge `everfrost`↔`qeytoqrg`. It only catches near-misses — a *touching* false positive (`everfrost`↔`qrg`) scores below the threshold and needs other evidence.

**What actually resolves a suspect edge is removal impact, not gap size.** Ask "if this edge goes, what becomes unreachable, and how much longer is the detour?" An edge whose removal cuts the graph is almost certainly real — the author drew those zones adjacent *because* they connect — and that settled 7 of the 11 flagged edges without needing a human. East Karana ↔ North Karana severs 16 zones as the east-west bridge of Antonica, so its 41-unit gap is stitch imprecision. Only edges that strand nothing need game knowledge. Lead with impact analysis; it is cheaper to compute and more decisive than either gap or weld-only-ness. **But it cannot rule on a false edge whose alternative is also false, and that is how `cauldron`↔`lfaydark` was mis-argued** — it was dropped on the grounds that Castle Mistmoore offered a same-cost alternative, and `cauldron`↔`mistmoore` turned out to be a proximity artifact too. When impact analysis leans on a specific alternative route, check that route's edges before trusting the ruling.

**Each zone's own detail map already lists its exits, and that is the primary source for adjacency.** `detail/*.json` labels beginning `to_`/`from_` are zone-transition markers, and `resolveZone()` turns them into zone keys — which is what `znorm`/`ZIDX`/`ZALIAS` exist for. Cross-checking the walk graph against them corroborates 73 of 76 edges; the three it could not are all now removed, and one edge it named that the graph lacked (`feerrott`↔`rathemtn`) is now added. Geometry welds cannot see any of this, which is why `derive_travel_graph.py` missed all four. It is evidence rather than proof in both directions — a map may simply not have drawn a label, and one label puts the Innothule connection on Lower Guk where the authored `guktop`↔`innothule` is right — so it proposes and a human disposes, same as the weld detector. **The reason a label can be absent is structural: these markers live in the pack's separate `_1` annotation layer, not in the map geometry** (see the provenance rules in [`../../AGENTS.md`](../../AGENTS.md) → Licensing boundary, and the measured counts in [`pack-import.md`](pack-import.md)), so a pack that never authored that layer for a zone yields no exits for it while its outline is perfectly complete. Every ruling belongs in `overrides` or `--audit` reports it forever.

**`overrides.added` holds two different kinds of ruling, and the second needs saying out loud
because the entry itself cannot.** Seven of the nine are game knowledge — *these zones do or do
not connect in EverQuest*, decided against a proposal the geometry got wrong. But
`ecommons`↔`nektulos` and `lavastorm`↔`nektulos` are not that: those connections were never in
doubt. They are ruled in because **the drawing stopped supporting them.** Nektulos Forest was
re-imported from a 2 931-segment trace replacing a crude 450-segment placeholder whose extent
overshot the real zone by ~1 256 units; the old outline *abutted* both neighbours (17.1 and 7.6
units, inside `LINK_THRESH`) and the accurate one falls 326 and 732 short. Nothing was ever
connected by a drawn connector there — the weld *was* the connection, and weld detection is the
only thing that ever inferred those two edges.

Two consequences. The zones now render with a visible gap, which is a **placement question, not
a routing one**, and it was deliberately left alone: a `zoneXf` translation can only trade one
gap for the other, since the shortfall is at opposite ends. It is adjustable in the editor by
anyone, in either edition. And a future re-import or refit that makes the outlines touch again
will make these two rulings unnecessary — at which point `--audit` says so, which is exactly what
the staleness report is for.

**A `spire`/`ring`/`portal` hub marks where you *arrive*, not where you cast from.** Wizard and druid ports are cast from anywhere, so those hubs are arrival markers and the route's `stops` are destinations — which is why `topology:"anywhere"` is the accurate model for them rather than a convenient approximation. Plane of Hate and Plane of Sky are wizard-portal-only with no hub at all, and are `anywhere` destinations for the same reason; Plane of Fear has a real portal hub in The Feerrott and so is a `line` from a specific origin. The template's `ENTRYHINT` already encodes that distinction.

**A `capability` asks what the user *is*, not what they are carrying.** Consumable requirements are deliberately **not** capabilities. The Plane of Hate and Plane of Sky teleports consume a soulstone and a cloudy stone respectively, and that was briefly modelled as its own `alterplane` capability before being collapsed back into plain `wizard`: gating on it makes the planner interrogate the user's inventory before it will plan anything, which is the wrong trade for a routing tool. The requirement lives in the hub's `note` instead, to be surfaced on the itinerary leg — inform rather than interrogate. Do not "fix" this by re-adding a reagent capability.

**`anywhere` is directed.** "Reachable from any zone" lets you port *to* a stop from where you stand; the edge does not run backwards. Modelling it as an undirected clique implies you can travel between two arbitrary zones by bouncing off a shared destination, which silently over-reports connectivity — `verify.py travel` therefore excludes `anywhere` stops from its component computation and tracks them as "has a way in" instead. Any pathfinder must union those destinations into each node's neighbours *per hop* rather than baking them into the adjacency.

**A vehicle costs the walk to it as well as the ride, and that is `routes[].access`.** A dock, ring or spire sits somewhere *in* its zone, not at the centroid, so boarding or leaving one is real walking that a flat vehicle cost priced at nothing — measured 1.1 to 32.4 units, and West Karana's wizard spire alone is 8 097 units from that zone's centroid, more than a whole port. `access[i]` is a per-stop array parallel to `stops`/`hubs`, **authored** and derived by `--recost`, never measured at runtime: a user can drag a hub in their own copy and their customisation must not reprice their routing. A `line` or `clique` leg pays **both** ends; an `anywhere` port pays only the **arrival**, which is the same fact that makes its `hubA` null — it is self-cast from where you stand. A stop whose hub is absent from `data/` costs 0, not because there is no walk but because nobody has placed the pier (East Freeport is the live case); inventing an `x,y` would be worse than recording the gap.

**A portal you must physically walk to is not `anywhere`, and needs no new machinery.** Model it as a `line` or `clique` with a hub on the *origin* stop and `access` prices the walk to it — Timorous Deep's portal room is the case in point. `anywhere` means self-cast, and its defining property is precisely that there is nothing to walk to.

**`TARR` entries must take their cost from the step, not from `r.cost`.** The arrival array carries its own `cost` field for relaxation, so building it from the bare route cost while the step folds in `access` prices the walk out of the ring at zero *and* shows it on the itinerary — the same "one number, carried with the step that explains it" invariant as the parallel-edge rule in [`travel-runtime.md`](travel-runtime.md) ("Adjacency is a per-node edge *list*") — which is where that rule now lives, and which this line previously mis-cited as being above it.

**A transport route does not require a hub.** `routes[].stops` is keyed on zones and `routes[].hubs` is an optional parallel array that accepts `null` per stop, so a dock with no hub in `data/` is still routable — East Freeport ships that way. This matters because the alternative reading ("add a hub first") means inventing an `x,y` for a pier nobody has placed. Hubs are the visual anchor, never the routing identity; the boat waypoint zones (`oot`, `erudsxing`, `timorous`) carry no hub at all.

**`TRAVEL` needs no `/*__DATA_*__*/` sentinel** — nothing mutates it and `getPristine()` snapshots the live document, so the injected value already rides along in a standalone export. Its declaration placement in `src/template.html` is load-bearing in two directions at once: **inside** the span `cmd_strip` excises (so its payload isn't scanned for FORBIDDEN tokens) and **outside** every data sentinel block (because `exportStandaloneHTML` rewrites the whole `__DATA_ALL__` block as `ALL/META/DETAIL` only, and would drop anything sharing that line).
